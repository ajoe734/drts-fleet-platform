# DRTS Platform — Cross-Surface E2E Suite

This directory holds the stateful cross-surface scenarios that stitch together
tenant, ops, driver, billing, and tenant-boundary evidence.

Use it together with:

- `docs/04-uat/fbp-014a-e2e-matrix.md` for the detailed scenario design
- `docs/03-runbooks/phase1-workflow-acceptance-release-gates.md` for release-gate interpretation
- `support/sidecars/FBP-014B/FBP-014B-LIVE-EVIDENCE-PACK.md` for the latest live staging rerun

## Gate Role

The E2E suite is not "all of release" by itself.

It serves three purposes:

1. prove cross-surface ID continuity for named workflow families
2. make cross-tenant safety reviewable
3. keep external-adapter and manual-only flows explicit instead of silently passing them

## Important Boundaries

- `E2E-001` and `E2E-004` are the release-grade live staging anchors.
- `E2E-002` is deterministic for the sandbox adapter and should not be treated as live adapter proof. External forwarder credentials, real relay latency, and partner-side receipt/settlement ownership remain separate gates.
- `E2E-003-phone-recording-filing.sh` proves the repo-local phone-order/recording/export/filing chain in sandbox mode, but does not claim live CTI provider media, staging scheduler activation, or external retention execution.
- `E2E-006-driver-multi-platform.sh` creates its own mixed owned+forwarded driver work: owned dispatch is assigned from runtime candidates, forwarded work is broadcast through the sandbox adapter, and driver visibility is verified across `/driver/tasks` plus `/driver/task-views`. Real Android/iOS device evidence remains covered by `EXT-003`, not by this shell proof.
- `E2E-008-partner-booking-cutover.sh` may warning-skip without a seeded ingress key. A skipped run is not pilot cutover evidence.
- `E2E-009-prod-rail-dry-run.sh` verifies the production rail contract only; production launch requires a real approved deploy, health evidence, monitoring evidence, and rollback proof.
- `E2E-010-governance-aware-billing-reporting.sh` is a repo-local default proof, not live staging uplift. The uplift to `PASS (live staging evidence)` remains blocked until a governed staging rerun produces reviewer-readable invoice/report artifacts and a green `STRICT_VERIFICATION_BODY=1` result. Default-mode runs still record each verification-body field as a literal value or `NOT_POPULATED`; the current strict blockers are `legacy_unmapped`, `quotaUsageDelta`, `partnerProgramCode`, `eligibilityVerificationId`, and `platformEarningsRef`. The script hard-fails on the contract regressions named in `FIN-GOV-SPEC-001`: cost-center attribution dropped from the booking read-back; driver lifecycle cannot reach completion after dispatch+assign accepted; invoice does not include the just-completed governed `orderId`; no `generate_tenant_invoice` audit entry for that invoice (FG-08); or a cross-tenant fetch of the invoice returns 2xx instead of 4xx (FG-09).
- `E2E-011-platform-admin-control-plane.sh` is the `WF-ADM-001` executable proof. It must not be warning-skipped: the scenario creates its own tenant, partner entry, pricing rule, feature-flag override, and rollout evidence, then verifies mutation and rejected-attempt audit rows.
- `E2E-012`, `E2E-013`, and `E2E-014` should be treated as repo-local proof until an explicit staging evidence pack records the runtime, command, evidence log, and gate interpretation. `E2E-012` still records tenant-business report row fields as soft evidence because report artifacts preserve filters/artifacts but do not yet materialize the dedicated row schema.
- The retired `apps/tenant-portal-web` shell is never a production verification target.

## Running

```bash
./tests/e2e/run-e2e.sh
./tests/e2e/run-e2e.sh --suite 001,004
./tests/e2e/run-e2e.sh --suite 009
./tests/e2e/run-e2e.sh --dry-run
```

Use a bare origin in `E2E_API_URL` and provide `E2E_AUTH_BEARER_TOKEN` when
staging ingress requires identity.
