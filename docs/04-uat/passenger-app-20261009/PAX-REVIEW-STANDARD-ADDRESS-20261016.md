# 審查叫車入口的一般地址與目前位置

共享環境開啟審查模式時，原叫車頁固定使用兩個演練點，無法操作已存在的一般地址搜尋與「使用目前位置」。本次在叫車表單增加「演練選址方式」：預設固定演練點，另可選一般地址搜尋與目前位置。

切換方式會清除上、下車點，保留預約時間；回到修改畫面則保留所選方式與地點。選址方式只存在同一份表單草稿，不改帳戶、API權限、服務區、費率、預約或付款規則。普通非審查入口照原有方式使用一般地址與目前位置。

一般選址沿原地址搜尋／解析／反查、報價及建單 API。圖資依本環境設定；簡訊、車司資格、司機定位、支付及通知仍依原演練配置。瀏覽器目前位置與司機行進 GPS 是不同來源。

驗證包含兩個 jsdom 整合案例：切換清除舊點、原表單定位拒絕後可重試、真實 BFF 呼叫鏈傳入座標、報價後返回修改保留方式。單元測試使用既有合成 HTTP 邊界，不當作共享環境證據。

既有 additional 旅程保留原 D/E 32 階段，追加 F 七階段，共39階段。F沿原乘客登入與付款方式：

1. 原固定點切換一般選址，確認地點清除、不能送出未選址的報價。
2. Chromium真實 geolocation API 回報拒絕，原表單顯示提示且不送 reverse。
3. Chromium以明示模擬的裝置座標授權定位，原 reverse API 接收同座標。
4. 一般下車地址搜尋並選取真API候選；原選址元件直接使用候選座標，後續報價另核對同座標，不假稱有額外 resolve 請求。
5. 原報價 API 收到目前位置；返回修改保留一般方式及地點。
6. 再報價並用原確認表單建立新的 F 訂單，讀回同一座標與真 orderId。
7. 未派遣前由原乘客畫面取消，同一訂單由乘客／調度讀回 cancelled，無付款與評價；沒有製造 Driver 任務。

沒有攔截或模擬內部 API／訂單，也沒有直接 SQL 寫入。原ABC48腳本、零重試與時限不變；新增兩張F原圖及一份具名座標／報價／訂單facts。CI與共享環境各須自己的新訂單及產物，不互相替代。這不證明實體裝置 GNSS、道路行程、所有圖資失敗／超區或真15分鐘報價到期。
