# PASSENGER-LIVE-TRACKING-20261017

乘客與司機共用同一筆後端訂單後，乘客仍只讀取指派當時的 ETA／定位新鮮度。
首輪 H 原圖出現司機回報 fresh、乘客卻顯示延遲；實際讀回的 assignment.eta
仍為指派當時的 missing。這是內部資料串接缺項，不能歸為缺少外部 GNSS。

新 `PassengerRideTracking` 與指派交易的不可變 disclosure 分開，帶出同一
assignmentId／driverId／vehicleId、現有 Regulatory Registry 的最新位置與新鮮度，
以及現有距離估算器計算的接客 ETA。帳戶及 token 入口均使用；指派快照、報價與
車司資料不被改寫。位置暫時讀不到時仍可讀原行程、顯示缺定位，不能借舊接客估時。
低精度／舊位置不顯示新接客估時，抵達／行程中不顯示接客 ETA，完程／取消停止追蹤。

原有三秒事件串流會比較即時位置及新鮮度：同一次指派的新位置會發出
`driver_location_updated`，估時改變發出 `eta_changed`；相同定位不因查詢時間改變
而重複發送。Web 與手機版均以 GPS 原始記錄時間計算延遲，不能用串流接收或重新
連線時間把舊定位標為新位置。事件順序、原 orderId 與 assignmentVersion 保持原契約。

Web 位置示意與手機版缺少外部地圖 renderer 時的示意圖，使用實際回報的座標放置車輛。
接客前指向上車點、行程中指向下車點；明示「位置示意」，線段不冒充道路導航。
既有原生地圖 renderer 存在時仍優先使用，並收到相同即時資料。外部地圖／實體 GPS
驗收與本次內部串接分開；沒有定位就不放入虛構車輛標記。

本機可跑的 28 個新增案例涵蓋原 service／SSE、Web／手機投影、座標示意與掛載中
Web 原頁，另驗手機畫面與既有案例。初始 13 案在舊來源全部失敗，保留重現報告。
本機不啟動 API／PG／瀏覽器／Metro 等產品環境。

完整 CI 另揭露兩個既有案例的銜接問題：建單回傳欄位清單須加入新 tracking 欄位，
且尚未指派時明確為 null，原交易／帳戶／歷史檢查維持；跨實例讀取測試的 SQL 邊界
回傳不完整指派時，新定位程式不應讓整筆訂單讀取失敗。缺 driver／vehicle 身分時
回定位不可用、不補造身分；缺路線時仍可帶出實際位置，但不產生接客 ETA。
這是合成 SQL 回應的回歸，不宣稱已在真實資料庫觀察到該種舊資料，完整 UC08
駕駛資料缺漏的實際觸發及原頁演練仍須另驗。
