# 乘客網頁：使用目前位置作為上車地點

一般預約頁原先只能搜尋地址或手動選點，未接上瀏覽器定位。本次在上車地點加入「使用目前位置」，由乘客點擊後取得裝置座標，再呼叫既有 passenger client／BFF 的 reverse geocoding。地址顯示在原 AddressMapPicker，沿原試算、費用確認與建單流程送出。

定位成功保留裝置的精確座標與精度，以地址服務回應補上地址與既有來源欄位。定位錯誤、拒絕、逾時、不支援或地址解析失敗均保留原選址，顯示可重試與搜尋地址的提示；不以假位置或樣本地址代替。使用者手選新上車地點、進入其他畫面或開始送出後，較晚回來的定位／地址結果不覆寫選擇。等待定位期間修改的下車點與時間也保留。

既有 demo／review 的明示合成起訖選單維持原流程。未更改原認證、session、CSRF、服務範圍、運價、預約前置時間、付款政策或測試逾時設定。

## 來源驗證

- 新增測試最初 12 例在舊產品因缺少定位按鈕失敗；後續新增兩例延遲 HTTP／無效地址，修補後合計 14 例通過、零跳過。
- 測試掛載真正 BookingScreen、AddressMapPicker、PassengerBookingClient 與 BFF；只模擬瀏覽器定位與外部 API HTTP。成功案例一路核對 reverse 的座標、原 quote request 與原 booking request。
- 涵蓋拒絕、定位不可用、逾時、不支援、無效座標、解析服務錯誤與重試、401 原登入導向、晚到的 GPS／HTTP、修改下車點／時間及離開頁面。
- 既有叫車／shell 回歸、typecheck、lint 與完整 CI 結果分別保存。此處不把 jsdom／HTTP 邊界測試稱為道路、真機或共享環境的新流程驗收。

## 人工操作補驗

1. 於一般預約頁點「使用目前位置」，使用瀏覽器原生定位提示，再確認上車位置、搜尋下車點及預約時間。
2. 沿既有試算與費用確認送出新單，核對上車座標；服務範圍仍由原後端判定。
3. 拒絕定位後確認原地址保留且仍可手選；定位或地址服務不可用時確認能重試。

人工真機與共享部署後的操作另取得證據。既有共享 v5 三角色新單與兩份完整合成 E04 的通過結果保留，不借用為這項新定位功能的部署信用。

## 初次點擊與畫面初始化的時序

後續同版完整回歸另捕獲一次定位負向案例失敗。初始 passive effect 原先無條件作廢目前請求；若使用者在該 effect 前已點按鈕，第一個定位回應會被當作過期結果忽略，連錯誤提示也不會出現。

新重現案例在初次畫面提交時點擊原按鈕，確實取得 native callback，然後送回拒絕定位：舊產品無法顯示原錯誤提示。修補只在選址或送出狀態實際改變時取消請求；初始值不再作廢第一個請求。原十四例及全部斷言、時間上限保留，新增此重現案例後合計十五例；修補與完整回歸結果獨立保存。
