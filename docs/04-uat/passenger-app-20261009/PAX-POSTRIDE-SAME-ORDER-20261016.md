# 完程後調度讀回與乘客遺失物案件驗收

既有三角色演練已實跑同一後端訂單，但 A/B 完程後的調度圖片保留了較早的人工快照，遺失物表單亦未走過完整瀏覽器鏈。本次沿用原三筆訂單與既有登入／派遣／付款流程，補驗這兩個未證步驟。

1. A 完程、付款與五星後，調度按原「讀回同單」，畫面及調度 API 均須讀到原 orderId 與 completed，才擷取原 A 三角色證據。
2. A 乘客從原行程開啟「客訴與遺失物表單」，選尋找遺失物、填合成雨傘與說明、同意聯絡，再由真表單 POST 建立 PAX 案件。
3. 調度以該新 caseNo 從真 API 讀回 app／lost_and_found／new、同一 relatedOrderId 及實際描述，再由真正案件頁確認原訂單連結及描述。只顯示 URL 中的案件號不足以通過。
4. B 完程但付款首敗時，調度亦必須按原讀回顯示原 orderId／completed。B 原低分案件頁另驗原訂單連結。

原三單、48 個進度階段、既有斷言、零重試及所有 timeout 均保留。新增附件只包含兩張合成遺失物畫面與選定的同單案件欄位；不表示真人聯繫、失物歸還、客服處理或案件結案已完成。只有實際 hosted 結果通過後才可更新交通局材料的 UC15 證據；本文件與測試修改本身不提供完成信用。

執行沿原 GitHub hosted CI 的 `playwright.pax-review-shared-order.config.ts`；不在工作 VM 啟動產品、資料庫或瀏覽器伺服器。新版本尚未部署前，既有共享 v5/v6 證據保持各自版本範圍。
