# 完程後調度讀回與乘客遺失物案件驗收

既有三角色演練已實跑同一後端訂單，但 A/B 完程後的調度圖片保留了較早的人工快照，遺失物表單亦未走過完整瀏覽器鏈。本次沿用原三筆訂單與既有登入／派遣／付款流程，補驗這兩個未證步驟。

1. A 完程、付款與五星後，調度按原「讀回同單」，畫面及調度 API 均須讀到原 orderId 與 completed，才擷取原 A 三角色證據。
2. A 乘客從原行程開啟「客訴與遺失物表單」，選尋找遺失物、填合成雨傘與說明、同意聯絡，再由真表單 POST 建立 PAX 案件。
3. 調度以該新 caseNo 從真 API 讀回 app／lost_and_found／new、同一 relatedOrderId 及實際描述，再由真正案件頁確認原訂單連結及描述。只顯示 URL 中的案件號不足以通過。
4. B 完程但付款首敗時，調度亦必須按原讀回顯示原 orderId／completed。B 原低分案件頁另驗原訂單連結。

原三單、48 個進度階段、既有斷言、零重試及所有 timeout 均保留。新增附件只包含兩張合成遺失物畫面與選定的同單案件欄位；不表示真人聯繫、失物歸還、客服處理或案件結案已完成。只有實際 hosted 結果通過後才可更新交通局材料的 UC15 證據；本文件與測試修改本身不提供完成信用。

## 原圖發現的案件歷程缺陷

首候選 d925 的真 PG／瀏覽器驗收通過，但原始遺失物案件畫面顯示新建、尚未指派的案件已完成分派，且虛構「轉入合規佇列」活動。程式將 `getComplaintTimeline` 從 SDK 實例取出後直接呼叫，遺失 `this` 而讀取失敗，再套入預製活動。新建與已關閉案件的進度計算亦不符合實際狀態。

沿原方法呼叫與進度計算抽出的回歸重現為 9 例中 4 失敗。修補保留 SDK 接收者、依六種真實案件狀態顯示進度，只呈現實際 API 活動；取得歷程失敗時顯示暫時無法載入。案件本身讀取失敗也顯示可返回列表的狀態，不再放入其他訂單／通話的預製案件。

新建案件的瀏覽器驗收另要求後端僅有 `case_created`，畫面沒有虛構佇列活動，進度只有建立完成、分派待處理、調查／結案未開始。這些檢查通過前，d925 舊畫面只作缺陷證據；原案件命令、狀態轉移及存取政策均未修改。

## 既有單元測試夾具的啟動順序

c53 自己的正常 CI 成功，真 PG／三角色瀏覽器也驗證了修正後的單一建立活動與新建進度。整合 CI 另在既有 `clamd-entrypoint.test.ts` 第三例失敗：初始 marker 時間戳是現在，預期的初始簽章則是兩日前。原夾具先 spawn 模擬程序，才寫初始簽章與 mtime，存在子程序讀到半套初始資料的排程窗口。

本次讓原14例先完成初始檔案、時間戳及共存版本的準備，再啟動同一模擬程序。原98個 assertion 呼叫、測試名稱、wait bounds及 timeout 的 AST 均相同，修後原14例零跳過通過；scanner、gateway與既有安全規則沒有修改。此項只證明單元夾具修補，不代替真實掃描引擎驗收。

執行沿原 GitHub hosted CI 的 `playwright.pax-review-shared-order.config.ts`；不在工作 VM 啟動產品、資料庫或瀏覽器伺服器。新版本尚未部署前，既有共享 v5/v6 證據保持各自版本範圍。
