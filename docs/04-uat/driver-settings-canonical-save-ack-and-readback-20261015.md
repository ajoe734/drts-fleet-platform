## 1. Authority & Scope Boundary

1. **Root Cause (`C060-F1`)**:
   - `apps/driver-app/app/settings.tsx:244-302,368-448` (`loadAll` and `handleSave`) already awaits `client.updateDriverSettings(driverId, buildSettingsCommand(settingsValues))` via `Promise.allSettled` and handles full success (`儲存成功`), full failure (`儲存失敗`), and partial failure (`部分儲存成功`) while keeping failed sections dirty for retry.
   - However, on the backend:
     - `DriverSettingsService.updateSettings` (`apps/api/src/modules/driver-settings/driver-settings.service.ts:54-104`) mutated `this.settings` in memory immediately, invoked `this.persist(updated)` as a detached `void this.repository.upsert(settings).catch(...)` promise that swallowed rejections after logging, emitted `recordAudit` (`update_driver_settings`), and returned synchronously.
     - `DriverSettingsController.updateSettings` (`apps/api/src/modules/driver-settings/driver-settings.controller.ts:77-102`) synchronously wrapped the unawaited result in `toApiSuccessEnvelope(...)`.
   - Consequently, delayed or rejected writes to `ops.phase1_driver_settings` still produced an immediate HTTP 200 ACK and `update_driver_settings` audit, caused `settings.tsx` to alert `儲存成功` and mark preferences clean while persistence was pending or failed, allowed failed writes to poison in-memory `getSettings`/`shouldDeliverNotification` decisions, and caused fresh service reconstruction (`onModuleInit` -> `repository.loadAll()`) to revert to older durable records.

## 2. Implementation Summary

1. **`DriverSettingsService` (`apps/api/src/modules/driver-settings/driver-settings.service.ts`)**:
   - Added per-driver write serialization (`private readonly settingsWrites = new Map<string, Promise<void>>()` via `enqueueSettingsWrite`) so overlapping same-driver partial updates stage from the latest committed state without clobbering fields omitted by later patches, while isolating different drivers so one driver's slow write does not block another's.
   - When `this.repository?.isEnabled()` is true, `updateSettings` awaits `this.persist(updated)` (`await this.repository.upsert(updated)`) **before** publishing to `this.settings` or emitting `this.recordAudit(...)`.
   - If `this.repository.upsert(updated)` rejects, `this.persist` calls `this.repository.reportPersistenceFailure(error, "update_settings")` and rethrows `error`. Neither `this.settings` nor `auditNotificationService` is mutated, and the per-driver queue recovers cleanly for subsequent retries.
   - If a transport error occurs after the database server has committed the row (uncertain commit outcome), `updateSettings` still rejects honestly without emitting a false 200 ACK, false audit log, or unacknowledged cache mutation, and without pretending that throwing in JS rolled back SQL; canonical reconstruction (`onModuleInit` / `loadAll`) reads the committed row from `ops.phase1_driver_settings`, and retrying the save converges memory, audit, and storage.
   - When `!this.repository?.isEnabled()` (explicit no-DB / disabled repository mode), `updateSettings` preserves the existing synchronous in-memory update and audit behavior and resolves `Promise<DriverSettings>`, imposing no global PostgreSQL precondition.
   - Defensively clones `preferredAreas` in `clone()` and `updateSettings()` and deduplicates loaded records by `driverId` (ordered by `updated_at DESC`) in `onModuleInit()`.

2. **`DriverSettingsController` (`apps/api/src/modules/driver-settings/driver-settings.controller.ts`)**:
   - Preserves the synchronous own-driver identity guard (`isDriverIdentityMatching(identity.actorId, driverId)` throwing 404 `DRIVER_SETTINGS_NOT_FOUND` on mismatch) and chains `.then((settings) => toApiSuccessEnvelope(settings, requestId))` on `this.driverSettingsService.updateSettings(driverId, command, requestId)` so the HTTP envelope resolves only after authoritative persistence ACK and rejects when persistence rejects.

3. **`DriverSettingsRepository` (`apps/api/src/modules/driver-settings/driver-settings.repository.ts`)**:
   - Preserves `isEnabled()`, `loadAll()`, `upsert(settings)`, and `reportPersistenceFailure(error, context)` against `ops.phase1_driver_settings`, normalizing `parseRecord` to accept both parsed JSONB objects and JSON string payloads.

4. **Existing Direct-Caller Test Adaptations**:
   - `tests/unit/driver-settings.test.ts`: added `async`/`await` to the 4 `service.updateSettings(...)` test cases; all original assertions preserved.
   - `tests/unit/system-remediation/sr-driver-gaps-20260911/driver-gaps-remediation.test.ts`: added `await` to the 2 `settingsService.updateSettings(...)` calls in Gap 3 (`C060`); all original assertions preserved.
   - `tests/unit/system-remediation/sr-qa-driver-001/driver-settings-notification-effect.test.ts`: added `await` to the 2 `settingsService.updateSettings(...)` calls; all original assertions preserved.
