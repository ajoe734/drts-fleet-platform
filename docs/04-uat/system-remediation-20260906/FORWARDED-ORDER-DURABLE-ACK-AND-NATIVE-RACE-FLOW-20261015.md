## Finding and repair boundary (C033-F1)

`ForwarderService.persistChanges` called `ForwarderRepository.persistChanges` fire-and-forget (`void ... .catch(reportPersistenceFailure)`). Every mirror-command mutator (`ingestExternalOrder`, `broadcastOrder`, `rejectForwardedOrder`, the success path of `relayDriverAccept`, `syncNativeStatus`, `engageManualFallback`, `completeReconciliation`) mutated the in-memory order, fired that unawaited write, then immediately recorded its success audit and returned the HTTP-success payload — all before the DB round-trip (when a repository/`DatabaseService` is configured) had actually acknowledged. `markSyncFailed`, used for sync/accept-relay failures, had the same unawaited-write shape.

Repair in `apps/api/src/modules/forwarder/forwarder.service.ts`:

- `persistChanges` is now `private async`, awaits the repository call, logs via `reportPersistenceFailure`, and rethrows (so callers can tell an unconfirmed write apart from a confirmed one) instead of swallowing the error.
- A new `persistOrFail(forwardedOrder, changes, context, requestId, acceptedDriverId?)` helper awaits `persistChanges`; on rejection it calls `markSyncFailed` with a `FORWARDER_PERSISTENCE_ACK_UNCERTAIN` error (retryable) — reusing the existing `sync_failed` / `manualFallback` / `reconciliationJob` vocabulary rather than inventing a new status or a fake provider receipt — and then throws a `502 FORWARDER_PERSISTENCE_ACK_UNCERTAIN` `ApiRequestError`. All seven mutators above now `await persistOrFail(...)` before recording their success audit, and are themselves `async`; `markSyncFailed` itself now awaits (and, since it is already the terminal honest-failure recording path, swallows) its own persistence attempt.
- `acceptForwardedOrder`'s existing C034-F1 catch branch (which re-reads the canonical order on `sync_failed`) already handles the new 502 the same way it handles an adapter relay failure, so a persistence-ACK failure during accept surfaces the same honest `sync_failed` outcome to the mobile caller instead of a fabricated `accept_pending`.
- `ingestExternalOrder` previously stored a *clone* of the new order in `this.forwardedOrders` while returning/mutating a separate local object; fixed to store the same object reference (matching every other mutator) so a persistence failure's `markSyncFailed` mutation is visible through `listOrders()`.
- The three adapter-health-only writes inside `verifyIncomingWebhook`, and the boot-time adapter-health seeding in `seedRegisteredAdapters`, are not part of the mirror-command lifecycle; they are wrapped in `try/catch`/`.catch()` (already logged by `persistChanges`) so they remain best-effort telemetry and do not throw unhandled rejections now that `persistChanges` rethrows.
- Controllers (`ingestInboundOrder`, `broadcastOrder`, `rejectForwardedOrder`, `reportSyncFailure`, `engageManualFallback`, `completeReconciliation`, `syncNativeStatus`) now `await` these now-async service methods before building their success envelope.

No repository SQL, contract, migration, auth policy, signature/provider-adapter or financial/shadow-ledger code changed. `ForwarderRepository.persistChanges` already awaited its `Promise.all` of real `INSERT ... ON CONFLICT DO UPDATE` statements keyed by `mirrorOrderId`/`platformCode`; the gap was purely that `ForwarderService` never awaited it.

## Round 2: reopen `7e24d35545bc442bb331fc56a30e6877` — R1-R4 fixes

Codex rejected candidate `10060a430ffd56a66086ce7f03eb9ba48c42fbb2` with four findings. All four were architectural gaps in the round-1 fix, not just missing tests: the round-1 code awaited the repository call, but every mutator still mutated the **shared live `this.forwardedOrders` entry in place** before/independent of that await, so (a) readers could observe the mutation immediately regardless of ACK timing, and (b) two concurrent commands on the same order could clobber each other's fields with no ordering guarantee. Fixed by reworking `ForwarderService` (`apps/api/src/modules/forwarder/forwarder.service.ts`) around two new primitives:

- `withLock(key, fn)` — a per-identity (mirrorOrderId, or `ingress:<platformCode>:<externalOrderId>` pre-creation) promise-chained mutex. Every mutating command now runs its "read canonical → build a clone draft → await durable ACK → commit" critical section inside this lock, so two commands on the same order can never interleave their persistence writes, and a later-queued command always observes whatever the earlier one actually committed. The lock is held **only** around this local section — never around an external adapter call — so a slow/stuck forwarder adapter can never block a native-authority sync on the same order.
- `commitOrder(order)` — the only place that writes into the live `this.forwardedOrders` array (insert or replace-by-`mirrorOrderId`), called only after a durable ACK (or, for the terminal best-effort `sync_failed` recording, after that write has been attempted). Every mutator (`ingestExternalOrder`/`createNewForwardedOrder`/`reconcileExistingIngest`, `broadcastOrder`, `rejectForwardedOrder`, `relayDriverAccept`, `reportSyncFailure`, `engageManualFallback`, `syncNativeStatus`, `completeReconciliation`, `markSyncFailed`) now builds its next state via `this.cloneOrder(canonical)` and never mutates the array entry directly.

### [P1 R1 / C033-F1] ACK-before-cache-publish

- Old `10060a4`: mutators (e.g. `broadcastOrder` line 542) mutated the object already sitting in `this.forwardedOrders` (obtained via `requireOrder`), then `await persistOrFail(...)`. `listOrders`/`getOrder`/driver task views read that mutation immediately, before the repository write landed.
- Fixed: every mutator builds a clone (`draft`) and only `commitOrder(draft)` — called from inside `persistOrFail`/`markSyncFailed` after the write is attempted — replaces the live entry. Readers cannot observe a draft ahead of its ACK.
- Repro/evidence: new test `does not let a driver-visible read (getOrder/listOrders/driver task view) observe the broadcast before its durable ACK resolves` in `tests/unit/forwarded-order-durable-ack-and-native-race-20261015/forwarded-order-durable-ack.test.ts` — asserts `getOrder`, `listOrders`, and `listDriverTaskViewsForRead` all still show `"received"`/not-visible while the repository write is a pending (unresolved) promise, then show `"broadcasted"`/visible once it resolves. Fails against old `10060a4` (reads would already show `"broadcasted"`), passes against the new candidate.

### [P1 R2 / C033-F1] `reportSyncFailure` honest durable-ACK

On its own persistence failure it overwrites `lastSyncError.code` to `FORWARDER_PERSISTENCE_ACK_UNCERTAIN` (message records both the original cause and the new failure) so the degraded record is distinguishable from a durably-recorded one. `reportSyncFailure` (the only *top-level* durable-ACK command built on `markSyncFailed`) checks `persisted` and throws the same `502 FORWARDER_PERSISTENCE_ACK_UNCERTAIN` `ApiRequestError` contract as `persistOrFail` when it is `false`, instead of returning success. Internal best-effort callers (`persistOrFail`'s own catch, `relayDriverAccept`'s adapter-unavailable/accept-relay-failed branches) are unchanged in throwing behavior — they already throw their own primary error regardless of `persisted`, matching the existing "no further fallback" terminal-recording contract.
- Repro/evidence: two new tests under `describe("C033-F1 reportSyncFailure: honest durable-ACK command")`. The failure-path test rejects `persistChanges` once and asserts `reportSyncFailure` **rejects** with `FORWARDER_PERSISTENCE_ACK_UNCERTAIN` (old `10060a4` would have resolved 200 with `data.status === "sync_failed"` here); the success-path test is new positive coverage (zero prior coverage existed for this command).

### [P1 R3 / C033-F1] Ingress retry: readback before re-attempting a write

- Old `10060a4`: a repeat `ingestExternalOrder` for the same `platformCode`+`externalOrderId` returned the cached entry unconditionally (`if (existing) return this.cloneOrder(existing)`), even when that cached entry's own creation write was never durably ACKed (`lastSyncError.code === "FORWARDER_PERSISTENCE_ACK_UNCERTAIN"`) — no readback, no retry write.

- Repro/evidence: two new tests under `describe("C033-F1 ingest retry: readback before re-attempting a write")`. ### [P1 R4 / C034-F1] Real repository-level race: accept vs. native authority

- Old `10060a4`: the in-memory "still broadcasted" guard in `relayDriverAccept` was checked only once, before the (now-awaited) `persistOrFail` call; the actual array mutation still happened on the shared live object with no lock, so a concurrent `syncNativeStatus` committing between that guard check and the accept write's repository round-trip (or vice versa) could land out of order — either clobbering an already-ACKed native result with a stale `sync_failed`, or leaving the durable row at `accept_pending` after a native cancellation had already been ACKed in memory.
- Fixed: `relayDriverAccept` calls the external `adapter.accept()` **outside** any lock (so it never blocks a concurrent native sync), then re-reads the canonical order **inside** `withLock(orderId, ...)` immediately before building/committing its own draft — for both the adapter-failure branch and the adapter-success branch. Because `syncNativeStatus` also runs its whole critical section inside the same per-order lock, the two commands can never interleave their repository writes for the same order: whichever reaches the lock first fully commits (success or `markSyncFailed` degraded-commit) before the other is even allowed to read canonical state, eliminating the out-of-order durable write rather than just papering over one interleaving.
- Repro/evidence: new `describe("C034-F1 real repository-level race: accept vs. native authority")` block builds a **real** `DatabaseService`-shaped double (`createGatedDatabaseService`) wired into a **real** `ForwarderRepository` and `ForwarderService`/`ForwarderController` (no repository-level fake, no duplicated SQL — the double only controls the `query()` promise for the specific `INSERT ... status = 'accept_pending'` call and records its real parameters). Driven through the actual mounted `controller.acceptForwardedOrder(taskId, driverIdentity("driver-dbrace-001"), {})` caller. Both the late-rejection and late-success branches are exercised by holding that one write open while a concurrent `service.syncNativeStatus(..., "cancelled_by_platform")` is issued, then resolving/rejecting the held write; both assert the final `service.listOrders()[0].status` is `"cancelled_by_platform"` (never a restored/clobbered `accept_pending` or a spurious `sync_failed` over an already-ACKed cancellation) and `acceptedDriverId` is preserved for dispatch follow-up. These fail against old `10060a4` (no lock existed, so the two writes could land in either order independent of the guard check) and pass against the new candidate.

## Round 3: reopen on candidate `9b8fc2f5fd72498048f9860af4cf6c1238392b5f` — R5 fixes

Codex rejected that candidate with three P1 findings. All three are genuine gaps left by the R1-R4 per-order lock: the lock correctly serializes commands that already key on the same `mirrorOrderId`, but (a) a batch's own sibling writes could still be left dangling past the lock release on a fail-fast rejection, (b) the ingress-retry path used a *different* lock key than every other command, so it was never actually excluded by the mirror lock at all, and (c) a caller-level catch block trusted the in-memory cache status without checking whether the write that produced it had actually landed.

### [P1 R4-2 / C034-F1] Batch write settlement: a rejected sibling write must not leave a dangling write behind

- Before (`9b8fc2f5f`): `ForwarderRepository.persistChanges` built one `Promise.all(writes)` per batch (the forwarded-order write plus its adapter-health sibling). `Promise.all` rejects as soon as the first promise rejects, but does not cancel or wait for the others — a still-in-flight sibling write kept running after the function had already thrown and the caller's `withLock` critical section had released. `ForwarderService.persistOrFail`'s catch ran `markSyncFailed` (committing a *newer* `updatedAt`) and returned/threw immediately, with no await on that dangling write at all. If the dangling write resolved later with an *older* `updatedAt`, the repository's unconditional `ON CONFLICT ... DO UPDATE` would silently resurrect it over whatever a subsequent command (e.g. a native sync that ACKed and released its own lock in the meantime) had already committed.
- Fixed:
  - `ForwarderRepository.persistChanges` now awaits `Promise.allSettled(writes)` and only throws (aggregating every rejection's message) after *every* write in the batch — including ones unrelated to the first failure — has actually settled. Nothing from this batch can still be in flight once the function returns/throws, so nothing can escape the lock that was protecting it.
  - The forwarded-orders UPSERT itself also gained a defense-in-depth guard: `ON CONFLICT (mirror_order_id) DO UPDATE SET ... WHERE EXCLUDED.updated_at >= ops.phase1_forwarded_orders.updated_at`. A write whose `updatedAt` is older than the row it would replace is now a silent no-op instead of an overwrite — this only ever makes an *older* write inert; a genuine newer native correction always carries a newer `updatedAt` and is never blocked by it.
- Repro/evidence: new `describe("R4 batch write settlement: ...")` in `tests/unit/forwarded-order-durable-ack-and-native-race-20261015/forwarded-order-durable-ack.test.ts`, using a real `ForwarderRepository` against a `DatabaseService` double whose order write resolves slowly (after a macrotask) while its sibling health write in the same batch rejects immediately. Asserts the slow order write had already settled *before* the batch (and the lock protecting `acceptForwardedOrder`) returned control — the specific defect the reviewer's probe demonstrated (`Promise.all` fail-fast leaving the order write dangling past the lock release, later landing a stale `accept_pending` over a newer native cancellation).

### [P1 R3-2 / C033-F1 + C034-F1] Ingress retry used a different lock key than every other command

- Before (`9b8fc2f5f`): `ingestExternalOrder` locked on `ingress:<platformCode>:<externalOrderId>`; every other mutator (`syncNativeStatus`, `relayDriverAccept`, `rejectForwardedOrder`, `broadcastOrder`, `reportSyncFailure`, `engageManualFallback`, `completeReconciliation`) locked on `mirrorOrderId`. Once a mirror identity existed, these were two independent lock domains — `reconcileExistingIngest`'s readback-then-decide critical section was never actually excluded from a concurrent `syncNativeStatus` on the same order, despite the R1-R4 doc above describing the per-order lock as closing exactly this gap. A readback that started before a native sync landed, but returned after, would unconditionally adopt (or rewrite as `received`) the pre-sync snapshot, discarding an already-ACKed native cancellation/correction. Separately, a `findOrderByIdentity` query *failure* (not a genuine empty result) was treated identically to "nothing durable exists yet," which could trigger the same stale rewrite instead of staying honestly uncertain.
- Fixed, in `reconcileExistingIngest` (`apps/api/src/modules/forwarder/forwarder.service.ts`):
  - Once a cached entry has a `mirrorOrderId`, the retry's readback-and-decide critical section now also runs inside `withLock(existing.mirrorOrderId, ...)` — the same lock key every other command uses — nested inside the outer ingress lock (different key, so no self-deadlock). Immediately after acquiring it, canonical state is re-read; if some other command already resolved the order away from the uncertain state while this retry was queued for the lock, that resolution is returned as-is instead of being overwritten.
  - `findOrderByIdentity` failures are now tracked separately from a genuine `null` result. A failed readback no longer falls through to the "nothing durable exists, safe to re-create" branch; it stays in the uncertain state for a later retry/reconciliation to resolve.
- Repro/evidence: new `describe("R3 ingress retry shares the mirrorOrderId lock with native sync (unified lock domain)")`. First test: an in-flight uncertain-retry's readback is held open while a `syncNativeStatus` call for the same order is issued concurrently; asserts the sync call stays unresolved while the retry holds the lock, and that its *later*-queued native cancellation (not the earlier-queued retry) survives as canonical once both complete — preserving `mirrorOrderId`/`platformCode`/`externalOrderId`/the native `providerReference`. Second test: `findOrderByIdentity` rejects; asserts the retry does not re-attempt the original write and the order stays `sync_failed`/`FORWARDER_PERSISTENCE_ACK_UNCERTAIN` rather than being reset to `received`.

### [P1 C033-F1 / mounted accept caller] A cache status of `sync_failed` is not proof the write that produced it landed

- Before (`9b8fc2f5f`): `markSyncFailed` always commits its draft into the live cache even when the write recording that state itself failed (by design — the cache has to say *something*, and it returns a `persisted: boolean` so callers can tell). But `acceptForwardedOrder`'s catch block, and the two `ApiRequestError`s `relayDriverAccept`/`persistOrFail` threw on a relay/persist failure, never threaded that `persisted` flag anywhere a caller could see it. `acceptForwardedOrder` decided purely from the in-memory cache (`status === "sync_failed" && acceptedDriverId === driverId`) whether to return a success envelope — so when *both* the primary write and `markSyncFailed`'s own fallback write were rejected (a genuinely doubly-uncertain outcome, durable row still whatever it was before this command), the caller still returned a normal `200` success envelope reporting `sync_failed`, instead of surfacing the persistence-uncertain error.
- Fixed: the two `relayDriverAccept` failure branches and `persistOrFail`'s catch branch now include the `persisted` value `markSyncFailed` returned in their thrown `ApiRequestError`'s `details`. A new `isPersistenceUncertainError(error)` helper reads that back via `error.getResponse()` (no change to the shared `ApiRequestError`/`toApiErrorEnvelope` — out of this task's write scope — just reading what it already exposes). `acceptForwardedOrder`'s catch now additionally requires `!isPersistenceUncertainError(error)` before returning the `sync_failed` success envelope; when the fallback write is itself unconfirmed, it rethrows instead.
- Repro/evidence: new `describe("C033-F1 mounted accept caller: persistence-uncertain failure must not become a success envelope")`. ## Round 6: reopen on candidate `c100603a1f59a9b74c44269cec8b5578e7dbd135` — a confirmed later write durably re-asserted a stale uncertain-ACK marker

The independent review of the exact `c100603a1` candidate confirmed the two Round 5 P1/P2 fixes hold, but reproduced one further defect: after both the `accept_pending` write and `markSyncFailed`'s own fallback write for an order are rejected (the genuinely doubly-uncertain cache state, `lastSyncError.payload.mirrorWriteAckUncertain: true`), a real, later `engageManualFallback` call that *does* durably land (INSERT ACK, `rowCount: 1`, success envelope) durably wrote that same stale `mirrorWriteAckUncertain: true` marker into the row it just successfully committed — because `engageManualFallback` clones its draft straight from canonical without touching `lastSyncError`. The next `accept`/`reject` call for the same driver on that order then read the marker back from this now-canonical row and incorrectly 502'd as still-uncertain (`persisted: false`), and a cold restart reloaded the same stale marker from storage, so the defect survived a restart too. `completeReconciliation`, which already explicitly sets `lastSyncError = null`, was not affected and was left untouched.

### Root cause

`persistOrFail` (the single durable-ACK gate every mutating command in this service goes through) committed whatever `lastSyncError` its caller's `draft` happened to carry, even on a fully successful write. `isMirrorWriteAckUncertain`'s marker is meant to answer "was the write that produced this cached content itself not durably ACKed" — but once *this* `persistOrFail` call has just durably ACKed `draft`, any leftover `true` marker from an earlier, different, unrelated write is self-contradictory: the content was in fact just confirmed. `engageManualFallback` (and, by the same structural gap, any other `persistOrFail` caller that forwards a cloned `lastSyncError` unchanged) could durably commit that contradiction. Each caller previously built its own `forwardedOrders` clone for the `changes` argument *before* calling `persistOrFail`, so clearing the marker only after `persistChanges` resolved would have been too late — the row already written (and what a restart reloads) would still carry it.

### Fix

- Added `clearStaleMirrorWriteAckUncertainty(draft)`, called once inside `persistOrFail` before it builds the durable row, clearing `lastSyncError.payload.mirrorWriteAckUncertain` back to `false` whenever it is stale. `markSyncFailed`'s own failure branch (the only place allowed to set the marker back to `true`) is untouched and still runs after this, in `persistOrFail`'s `catch`.
- `persistOrFail` now builds `forwardedOrders: [this.cloneOrder(draft)]` itself from the (now marker-cleared) `draft`, instead of trusting a pre-built clone each of its 8 call sites constructed independently — removing the structural gap that made the in-time fix impossible, and collapsing 8 duplicated clone call-sites into one. Call sites now pass only the remaining `extraChanges` (e.g. `adapterHealth`); none of them changed their actual persisted content otherwise.
- No new error code, HTTP status, schema, contracts, or `PersistForwarderChanges` field; `completeReconciliation`'s existing (and correct) explicit `lastSyncError = null` reset is unchanged.
