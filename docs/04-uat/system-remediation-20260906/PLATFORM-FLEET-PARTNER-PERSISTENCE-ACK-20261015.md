## Finding and repair boundary

In `apps/api/src/modules/fleet-partner/fleet-partner.service.ts`, `FleetPartnerService.createFleetPartner`, `updateFleetPartner` (including `active:false`) and `createDriverFleetAffiliation` previously published cache changes before their unawaited persistence helper completed. That helper reports and catches repository failures. The matching handlers in `apps/api/src/modules/fleet-partner/fleet-partner.controller.ts` immediately created normal success envelopes. The existing `FleetPartnerRepository.persistChanges` already awaits the selected SQL promises via `Promise.all`.

The three commands now await `persistMasterDataChanges`, which reports and rethrows the original repository error. Cache publication follows acknowledgement. Updates validate a private clone, so neither a rejected write nor a later invalid field mutates the prior record. A per-partner, per-service queue orders partial updates of that record and releases after either outcome; other partners and affiliations proceed independently. Successful publication merges into the current collection without restoring a stale array. This is local synchronization, without a new cross-instance gate or policy.

The three controllers await real records before constructing envelopes. The one existing direct controller test at `apps/api/tests/unit/fleet-partner.controller.test.ts` now awaits its affiliation response, retaining its driver assertions. Caller search: `rg -n '(createFleetPartner|updateFleetPartner|createDriverFleetAffiliation)\(' --glob '*.{ts,tsx}' apps packages tests`. The existing SDK, UI adapters and page callers already await HTTP; no further caller or shared SDK changes are needed.

`persistChanges` remains unchanged for initialization and revenue-rule callers. No repository, SQL, contract, auth policy, C103, pricing or financial policy is changed. Existing `foundation:write`, platform/ops realms, missing-master refusals, field/date validation, soft disable, affiliation normalization, cloned readbacks and both absent/disabled repository modes remain supported. V0026 uses generated partner/affiliation primary keys; existing code has no business-registration uniqueness check, and this repair introduces no new uniqueness policy.
