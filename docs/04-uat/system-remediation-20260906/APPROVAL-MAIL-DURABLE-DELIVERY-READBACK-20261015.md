## 2. Before / After Reproduction Summary

### Before Repair

`AuditNotificationEmailAdapter.deliver()`:

```ts
try {
  const queued = await this.deliveryService.enqueue({ ... });
  const receipt = queued.status === "sent" ? queued : (await this.deliveryService.dispatch(...) ?? queued);
  ...
} catch (error) {
  // Reached for BOTH a genuine enqueue failure (no durable record exists)
  // AND a dispatch-phase claim/ACK-persistence rejection (a durable record
  // from enqueue already exists).
  return {
    ...
    deliveryId: `error-${idempotencyKey}`,  // discards the real, already-committed id
    status: "failed",                       // fabricates certainty the provider never gave
    ...
  };
}
```

Reproduced with a `FileMailOutbox` wrapped so its 2nd `transaction()` call (dispatch's claim phase) throws: the adapter returned `deliveryId: "error-approval-notification:...:...:..."` and `status: "failed"`, even though `NotificationDeliveryService.get(tenantId, <real deliveryId>)` showed a genuinely stored `"queued"` record with zero attempts (no provider call was ever made). Reproduced again with the 3rd `transaction()` call (post-ACK persistence) throwing after a real provider accept: the adapter still returned the synthetic `error-` id and `"failed"`, discarding a receipt that actually held one `"started"` attempt and could not honestly be called a provider failure.

### After Repair

`deliver()` now wraps `enqueue()` and the `dispatch()` call in separate `try`/`catch` blocks (mirroring the already-shipped `TenantInvitationDeliveryService` C006 pattern):

- `enqueue()` throwing → nothing durable exists yet; the synthetic `error-<idempotencyKey>` id and `status: "failed"` remain correct (unchanged behavior).
- `dispatch()` throwing after a successful `enqueue()` → the catch returns the real `queued.deliveryId` / `queued.messageId` / `queued.status` (always `"queued"` at that point) / `queued.sentAt`, with a bounded `errorCode` derived from the dispatch exception. No `"sent"` or `"failed"` is fabricated for an ACK-unknown outcome.

Re-running both reproductions: the adapter now returns the real UUID `deliveryId`, status `"queued"`, and the same identity is confirmed resolvable through `NotificationDeliveryService.get()` directly and through `TenantPartnerService.getMailDeliveryReceipt()` (the existing SR-MAIL-DELIVERY-READBACK-20261001 readback endpoint) via the full `AuditNotificationService.dispatchApprovalNotification` per-recipient audit path.

### 5.2 Before / After Reproduction Summary (`N07-SRC-01`)

- **Before Repair**: In `TenantPartnerService.createBookingApprovalRequest` (`onSuccess`), after dispatching the `new_request` approval notification, the service triggered `void this.pollPendingApprovalTimeoutNotifications();` without attaching a `.catch(...)` handler. After `SR-MAIL-RETRY-SCHEDULE-20261001` R1-02 changed `executeApprovalTimeoutNotificationSweep()` to rethrow `ApiRequestError(HttpStatus.BAD_GATEWAY, "APPROVAL_TIMEOUT_SWEEP_FAILED", ...)` when `tenantPartnerRepository.loadState()` fails (so external HTTP scheduler triggers receive a `502` instead of a false-success `{ evaluated: 0, dispatched: 0 }`), `startApprovalNotificationPolling()` and `onModuleInit()` both attached `.catch(...)` handlers to their fire-and-forget `pollPendingApprovalTimeoutNotifications()` calls, but `createBookingApprovalRequest` (`onSuccess`) still used `void this.pollPendingApprovalTimeoutNotifications();`. Consequently, a repository read error during the post-create background poll emitted an `unhandledRejection` for `APPROVAL_TIMEOUT_SWEEP_FAILED` (502) even though `createBookingApprovalRequest` had already succeeded.
- **After Repair**: `createBookingApprovalRequest` (`onSuccess`) now attaches the same `.catch(...)` error-handling and logging pattern used by `startApprovalNotificationPolling()`:
  ```ts
  this.pollPendingApprovalTimeoutNotifications().catch((error) => {
    const message =
      error instanceof Error ? error.message : "unknown polling failure";
    this.logger.error(
      `Background approval timeout notification poll failed: ${message}`,
    );
  });
  ```
  Because `.catch(...)` is attached at the fire-and-forget call site rather than inside `pollPendingApprovalTimeoutNotifications()` or `executeApprovalTimeoutNotificationSweep()`, `this.approvalNotificationPollInFlight` continues to hold the underlying sweep promise:
  1. Post-create background sweep failures are caught and logged without emitting an `unhandledRejection` or invalidating the created approval request or its `new_request` notification.
  2. Explicit scheduler calls (`runApprovalTimeoutNotificationSweep()` / `POST /api/internal/scheduled-tasks/approval-timeout-reminders/run`) — both subsequent calls and calls coalescing onto an in-flight post-create sweep — still reject with `ApiRequestError(502, "APPROVAL_TIMEOUT_SWEEP_FAILED")`.
  3. Once repository reads recover, a subsequent sweep evaluates the persisted pending request and dispatches the `approaching_timeout` notification normally.
