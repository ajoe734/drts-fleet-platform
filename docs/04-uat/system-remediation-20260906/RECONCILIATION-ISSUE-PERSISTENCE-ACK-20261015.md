## Findings and repair boundary

`BillingSettlementService.createReconciliationIssue`, `assignReconciliationIssue`, `addReconciliationIssueComment`, `resolveReconciliationIssue` and `reopenReconciliationIssue` previously mutated the shared `this.reconciliationIssues` array (for create) or the shared record object returned by `requireReconciliationIssue` (for the other four) *before* calling `persistChanges`. Because `requireReconciliationIssue` returns a live reference into the shared array (not a clone), and `persistChanges`/`persistChangesRequired` already rejects and rethrows when the injected `BillingSettlementRepository` rejects a write, any rejected or still-pending canonical write left the in-memory cache (and therefore every `listReconciliationIssues`/`requireReconciliationIssue` readback and the controller response built from it) already showing the new issue, the new owner/status, the new comment, the new resolution, or the incremented reopen counter — a phantom state the durable store never actually has.

The fix stages the complete intended change in a private clone (`draft`) built off `cloneReconciliationIssue`, calls `persistChanges` with that staged clone, and only mutates the shared cache (`this.reconciliationIssues` prepend for create; `Object.assign(issue, draft)` for the other four, since `issue` is the live array reference) after the repository has acknowledged the write. On rejection, `persistChangesRequired` already rethrows (calling `reportPersistenceFailure` first when the repository implements it) and now nothing downstream has been touched — no array mutation, no field mutation, no audit log entry, because `recordAudit` is called after the (now successful) publish, exactly as before. The five production hunks changed are the five command methods only; `requireReconciliationIssue`'s own reference-returning behavior is unchanged (it has no other callers), `listReconciliationIssues`, `syncDerivedForwarderIssues`, `createIssueComment`, `mergeArtifactIds` and `persistChanges`/`persistChangesRequired` are unchanged.

A second, related gap: because the four read-modify-write mutators build their `draft` from the shared object's *current* field values and only write back after their own `await persistChanges(...)` resolves, two concurrent calls against the **same** `issueId` (e.g. two comments, or an assign racing a resolve) could both read the same pre-write snapshot and the later `Object.assign` would silently clobber the earlier one's change (a lost update), even though each individual write was itself correctly ACKed. This is the same class of race the already-merged `PLATFORM-FLEET-PARTNER-PERSISTENCE-ACK-20261015` (#2659) fixed for `FleetPartnerService.updateFleetPartner` with a per-record promise queue; the same pattern is applied here as `serializeReconciliationIssueUpdate`, keyed by `issueId`, wrapping the full body (including validation) of `assignReconciliationIssue`, `addReconciliationIssueComment`, `resolveReconciliationIssue` and `reopenReconciliationIssue`. `createReconciliationIssue` needs no queue: it only ever appends a brand-new object, so it never reads-then-writes an existing shared record. The queue is a local, in-process `Map<string, Promise<void>>`; it introduces no multi-instance, distributed-transaction or cross-service lock, and independent issues are never serialized against each other.

Deliberate noDB/demo behavior (no repository configured → `persistChangesRequired` returns immediately, mutation proceeds synchronously as before), the resolved→reassignment `RECONCILIATION_ISSUE_RESOLVED` denial, the not-resolved→reopen `RECONCILIATION_ISSUE_NOT_RESOLVED` denial, forwarder/shadow issue sync (`syncDerivedForwarderIssues`), and Finance create/assign/comment/evidence/resolve/reopen success-audit-after-publish are all unchanged in effect and covered by regression below. No other module (`generateDriverStatements`/C089, tenant invoice reader/C077, C080 batch workflow, parent payment/refund ledger) was touched; `rg -n 'requireReconciliationIssue\(' apps/api` confirms its only four callers are the four methods edited here.

## Regression design and reproducibility

`tests/unit/reconciliation-issue-persistence-ack-20261015/reconciliation-issue-persistence-ack.test.ts` calls the real `BillingSettlementService` methods under test. Only the external persistence boundary is doubled: a small `FlakyReconciliationIssueRepository` implements the exact `BillingSettlementRepository` contract the service depends on (`isEnabled`/`loadState`/`persistChanges`/`reportPersistenceFailure`) with an in-memory durable table, a `failNextPersist` toggle to reject exactly one write, and a `holdNextPersist()` gate to keep exactly one write in flight — the same "mock the repository contract, never the service logic" convention already used for this same service in `tests/unit/audit-artifact-durability-20261002.test.ts`'s `emptyRepository()` helper and for `FlakyDocumentArtifactStore` in its R5 suite.

10 cases cover: for each of the five commands, a rejected write followed by a healthy retry, asserting (a) the pre-write in-memory snapshot is byte-identical to the post-rejection snapshot (`toEqual`), (b) no audit log entry was recorded for the rejected attempt (`getAuditLogsSnapshot` filtered by `actionName`/`resourceId`), (c) the retry publishes the exact intended result with no duplicate comment/evidence/reopen-count, and (d) a **fresh** `BillingSettlementService` instance sharing only the same repository's durable rows (`onModuleInit` → `loadState`) reads back the identical published state. Two original-authority regressions (resolved-reassignment denial, not-resolved reopen denial) and one noDB/demo full-lifecycle regression (no repository injected at all) guard the preserved behavior from `before_after_requirements`. Two concurrency cases prove (e) an in-flight write on one issue does not block an independent issue's create, and (f) two concurrent comments on the *same* issue are serialized so the second starts from the first's acknowledged state instead of losing it — this second case would fail without `serializeReconciliationIssueUpdate` (the later `Object.assign` would overwrite the earlier comment).

These are in-process async-contract tests, not live PostgreSQL acceptance; no VM product/dev/preview/HTTP/browser/E2E/Docker/cloud/IAM/Operator process was started, consistent with the task's "no VM product/dev/preview/HTTP/PG/browser/E2E/Docker servers" instruction.
