# FLEET-PARTNER-ENTRY-CANONICAL-BINDING-20261019

Owner: Codex2. Reviewer: Codex. Source baseline: `4cf8eadadb4e74e736c1c5f88286645e0fa84aa0`.

## Problem and resulting behavior

The normal admin Entry create API previously ignored a supplied Fleet reference and generated `partner_<UUID>`. A normally issued partner credential therefore identified that unrelated Entry partner ID, rather than the existing Fleet master required by the Fleet portal. A valid principal and a matching Fleet selector are both still required; changing a selector alone does not establish authority.

`CreatePartnerChannelEntryCommand` now accepts an optional `fleetPartnerId`. Only an explicit reference on a `fleet_partner` Entry uses the new branch. Both canonical Fleet and Entry repositories must exist and be enabled. The Fleet repository performs a parameterized lookup against `admin.phase1_fleet_partners`, requiring physical `active = true`; the service also checks that the parsed record has the exact requested canonical ID and `active === true`. Missing, inactive, mismatched, unavailable or malformed references reject without Entry persistence, cache publication or success audit. Lookup and Entry write failures propagate. General unbound Entry creation retains its random ID and original no-database behavior.

The binding uses the existing slug mutex, cloned Entry, awaited `persistChangesRequired`, and cache/audit publication after acknowledgment. The stateless repository is locally provided by `TenantPartnerModule`, following the existing Owned Mobility pattern without importing the Fleet module. Its optional service injection is appended to preserve existing positional callers. No Update binding input or arbitrary `partnerId` input is introduced. Existing Fleet mutations and receipt/operator lookup are unchanged.

## Normal credential rail

An authorized administrator can use the existing create Entry API with an existing active Fleet reference, then explicitly request the first normal credential on that new Entry with the required existing scopes. The existing partner bootstrap endpoint derives its partner ID from the persisted Entry and scopes from that credential. Existing default scopes still exclude `billing:read`; issuing or rotating keys on existing entries is outside this change. Existing Fleet principal verification, requested/configured selector matching, revocation and Entry lifecycle checks remain in force.

The socket-free regression creates the Entry and first credential through the real service and repositories, then calls the real `AuthController.issuePartnerBootstrapSession`, JWT signer, bootstrap guard, session controller and Fleet `resolveFleetPrincipal`. Only SQL responses and the fetch transport to the session controller are controlled. Signing material and credential values are synthetic unit data. This test uses the JWT service's existing no-IdentityRepository unit mode; it proves normal issuance and signature/consumer wiring, not PostgreSQL identity-session durability or deployed login.
