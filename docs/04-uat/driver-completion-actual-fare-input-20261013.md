## Behavior and real call path

`TripScreen` renders the existing Canvas `Card`/`Field`/`Input` controls for explicitly reported start, distance, delay and night amounts, entered in NTD dollars with at most two decimals. `parseActualFareMinor` uses decimal digits and integer conversion without rounding. Blank is distinct from entered zero. All four components must be present if any capture is attempted; each minor amount and their sum must be safely representable. Invalid capture both disables the real native button and is rechecked in `handleAction` before persistence.

A non-fixed order also requires an independently entered aggregate, sent as `fare` with imported `PLATFORM_CURRENCY` (`TWD`). Neither the task's fare, quote, distance/time nor component sum supplies that value. Differing sums and totals are accepted without interpreting tolls. A fixed order has no editable aggregate override, omits `command.fare`, and retains `order.quotedFare` authority; a missing/invalid/currency-incompatible fixed quote blocks component capture. Allblank input omits both new properties and preserves legacy completion.

The existing completion metrics, proof, expense, identity, error and pending replay paths remain. Drafts are keyed to the actual task, reset at existing reset boundaries, and cannot be used with another task. The completion order must match the current task's order before requirements/fixed-price decisions are usable. New copy is confined to `driverStrings.trip`; accepted earnings strings are preserved.

Production chain tested: actual `TripScreen.handleAction` → `submitDriverTaskCompletion` → actual SecureStore JSON codec → reload of Driver API module state → `replayPendingDriverTaskCompletion` → actual `@drts/api-client.completeTask` → intercepted `fetch`. The actual mounted `usePendingCompletionReplay` is also exercised, including refusing an old task's pending request while another task is active.
