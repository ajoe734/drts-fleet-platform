## 平行與共用檔案規則

1. 不設「所有工作等第一波全部結束」的總閘門。每個任務只有真正資料契約或共用檔案的前置；roots即刻可做。
2. Owner/reviewer不同，六條現有lane輪配；supervisor可依idle/quota合法改派，不能拿初始owner當檔案鎖。每task獨立worktree、分支與測試namespace。
3. **serial_resources / write_scopes 是本包的檢查資料，不是假稱 supervisor 已有檔案鎖功能。** 真正防衝突靠已写入 depends_on 的序列，validator檢查所有重疊目錄／檔案必須有可達相依。
4. `packages/contracts` exports、client、OpenAPI只由SR-CONTRACT整合；`package.json`／lockfile由SR-DEPS；root module/新功能navigation由SR-WIRE。Worker需要新增共用寫入，先由supervisor增加scope和必要deps後再做。
5. 大檔明確序列：REFERRAL→MAIL-001（tenant service）；INVOICE→PROOF→FLEET-SETTLE（billing service）；ADMIN-ADAPTER→PLACARD（platform-admin service）；FLEET-DATA→CASE→SETTLE（fleet loader）。Academy用獨立adapter，因此不被帳務長鏈卡住。
6. 請假／學院／Host：小型design/contract完成後，三個backend與三個frontend可各自並行；只有真整合及導航等待SR-WIRE。frontend contract fixture只能驗UI契約，不能宣稱真流程完成。
7. 共享schema以獨立migration檔名及分配紀錄避免撞號；不能各自修改同一migration或已落地migration。
8. 與既有UV工作：不重造CTI、voice、持久化reservation/matcher或Postgres競態框架；必要依賴明列如下。既有task status/owner不由此script改寫。

## 真外部驗收與發布界線

9個live任務保持blocked：正式入口/身份、郵件、推播、storage/signer、金融/issuer、真maps、native真機、第三方forwarder、備份/還原/容量。SR-READINESS可平行完成準備報告，但它的done絕不代表帳號、裝置、收件匣、電話或雲端變更已獲授權。

所有live task等SR-RELEASE提供固定候選，再以同一business candidate驗證。SR-RELEASE只代表隔離local/dev閉環；SR-ACCEPT還等待所有本期live證據及既有UV-EXEC-028，不能把準備報告或mock當全系統上線完成。已授權測試租戶可做可回復建單/派車/狀態操作；不得碰正式訂單、真付款、外部人員訊息、真電話或prod rollout。缺具體必要授權時只暫停該dependent live項，不擋其他工作。

## 結案規則

- 每個issue以具體重現→fix/no-regression→review→同candidate CI→merge→必要live證據串起。若當前已修則交證據與meaningful regression，不創無必要改動。
- 驗收task發現缺陷時建立有範圍和追溯的implementation child，再由supervisor讓該驗收等待child；不得只寫「待辦」就done，也不得越界把一個驗收task改成全庫修復。
- `done`由canonical lifecycle推导，owner只handoff；cross-role、artifact bytes、provider receipt、DB回讀是證據，頁面200、typed方法或「有檔案」不是完整驗收。
- 七項範圍排除由SR-SCOPE記錄，沒有產品實作task：paused/retired、Phase2 ROC/AV、filing PDF/ZIP、regulator realm、eventbus/已核定狀態、簽核自動逾時等。
- 未做load/restore/true native或無正式身份，一律保留相應gate，不以縮小完成定義換done。
