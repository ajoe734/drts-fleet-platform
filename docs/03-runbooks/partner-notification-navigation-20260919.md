# Partner Notification Navigation Integration Guide

This guide explains how external partners can securely redirect passengers from a webhook notification directly into the correct embedded booking context (e.g. an active trip tracking screen or a past trip receipt).

## Authentication & Authorization

To resolve a notification navigation attempt, the partner service must call the DRTS Core API using their backend-to-backend API key. The passenger's client should **never** invoke this API directly.

### 1. Resolve Navigation Destination (Backend to Backend)

When a passenger clicks a notification inside your native application, your application should call your backend, passing the \`rideRef\` (provided in the webhook payload) and the \`partnerUserRef\` (the ID of the passenger in your system).

Your backend then calls the DRTS Core API to obtain a securely signed navigation artifact and destination URL.

**Endpoint:**
\`POST /api/partner/entries/{entrySlug}/notification-navigation/resolve\`

**Headers:**
\`x-api-key\`: Your Tenant API Key

**Body:**
\`\`\`json
{
  "rideRef": "rd_7e8b9a11...",
  "partnerUserRef": "partner_user_123"
}
\`\`\`

**Response (Success - 200 OK):**
\`\`\`json
{
  "data": {
    "handoffArtifact": {
      "handoffId": "handoff_...",
      "artifact": "b64url_string_here...",
      "tokenType": "SingleUse",
      "expiresIn": "120s"
    },
    "destinationUrl": "https://{entryHost}/api/referral/notification-navigation?artifact=...&entrySlug=...&screen=trip&orderId=..."
  }
}
\`\`\`

**Response (Failure - 403 Forbidden):**
If the request is unauthorized, the trip does not exist, or the user does not match the originally linked identity, the API will fail closed with a generic \`403 Forbidden\` error.

### 2. Client Redirection

Once your backend receives the \`destinationUrl\`, it should instruct your mobile application (or frontend) to open this URL inside the webview that hosts the DRTS embed. 

The BFF will automatically consume the \`artifact\`, establish a fresh HttpOnly session, and seamlessly redirect the passenger to the correct screen (e.g., active trip tracking or receipt page) based on the trip's current status.

## Error Handling & Security

- **Single Use:** The \`artifact\` generated by the resolve endpoint is valid for **120 seconds** and can only be consumed **once**. Ensure your webview loads it promptly.
- **Enumeration Prevention:** The API deliberately fails with generic errors to prevent scanning or guessing of \`rideRef\` and \`partnerUserRef\` pairs.
- **Fail Closed:** Logout, revoked identities, and inactive entries will all cause the resolve request to fail safely. Under no circumstances will a navigation failure automatically create a new order.
